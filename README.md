# Обмен данными между ПК по UDP multicast

Программа `exchange` раунд за раундом обменивается блоками данных между несколькими компьютерами в локальной сети и замеряет, сколько времени занимает каждый обмен. Задача: при размере блока 1024 байта уложиться в 200 мкс.

## Как работает

- Все узлы подключаются к multicast-группе 239.10.10.10, порт 5000. Пакет, отправленный в группу, сразу получают все узлы.
- Сначала узлы рассылают сообщения HELLO, пока каждый не увидит всех остальных.
- Потом идут раунды. В каждом раунде узел отправляет свой блок и ждёт блоки от остальных узлов за этот же раунд. Время от начала раунда до получения всех блоков записывается как `exchange_us`.
- У каждого пакета есть заголовок на 48 байт: номер раунда, номер отправителя, контрольная сумма CRC32 и значение счётчика.
- Каждый узел ведёт счётчик: берёт максимум из полученных значений и прибавляет 1, если все значения совпали. В конце узлы сравнивают итоговые значения (VERIFY). PASS значит, что все узлы прошли раунды синхронно и без потерь.
- Первые раунды (`--warmup`) в статистику не попадают.
- В конце программа выводит статистику и гистограмму задержек, а с флагом `--csv` сохраняет данные по каждому раунду.

## Сборка

```bash
gcc -O3 -g -std=gnu11 main.c -o exchange -lm
```

## Стенд

Три ПК с Ubuntu в одной локальной сети:

| ПК | --id | IP |
| --- | --- | --- |
| user | 0 | 192.168.10.1 |
| pc1 | 1 | 192.168.10.2 |
| pc4 | 2 | 192.168.10.4 |

Сначала проверяли обмен на двух ПК, потом на трёх.

## Подготовка системы

Со стандартными настройками Linux часть раундов шла дольше 200 мкс (вплоть до 1000 мкс), а узлы иногда расходились по раундам. Поэтому перед запуском на каждом ПК выполняли:

```bash
sudo systemctl stop irqbalance
for i in $(grep enp /proc/interrupts | cut -d: -f1); do echo 0 | sudo tee /proc/irq/$i/smp_affinity_list; done
sudo python3 -c "import time; f=open('/dev/cpu_dma_latency','wb',0); f.write(b'\0'*4); time.sleep(3600)" &
```

1. Отключаем irqbalance, чтобы прерывания не перекидывались между ядрами.
2. Закрепляем прерывания сетевой карты за ядром 0.
3. На час запрещаем процессору уходить в режимы сна, потому что выход из сна давал задержки.

Саму программу запускали на ядре 1 через `taskset -c 1`, чтобы прерывания сетевой карты ей не мешали.

Ещё пробовали `chrt -f 99` и `busy_poll`, но стало хуже. С `chrt` программа не давала ядру обрабатывать сеть, а `busy_poll` тормозил двухъядерный ПК user, и остальные узлы убегали вперёд по раундам. Поэтому от них отказались.

После перезагрузки все эти настройки сбрасываются.

## Запуск

Запускали одновременно на трёх ПК.

На user:
```bash
taskset -c 1 ./exchange --id 0 --nodes 3 --iface 192.168.10.1 --size 1024 --duration 2 --warmup 100 --csv /dev/shm/node0.csv
```

На pc1:
```bash
taskset -c 1 ./exchange --id 1 --nodes 3 --iface 192.168.10.2 --size 1024 --duration 2 --warmup 100 --csv /dev/shm/node1.csv
```

На pc4:
```bash
taskset -c 1 ./exchange --id 2 --nodes 3 --iface 192.168.10.4 --size 1024 --duration 2 --warmup 100 --csv /dev/shm/node2.csv
```

Параметры:
- `--size 1024` размер блока в байтах;
- `--duration 2` длительность теста в секундах;
- `--warmup 100` первые 100 раундов не учитываются;
- `--csv` файл с данными по каждому раунду.

CSV писали в `/dev/shm` (это оперативная память), чтобы запись на диск не влияла на замеры, а после теста копировали в папку проекта:

```bash
cp /dev/shm/node*.csv .
```

Все параметры: `./exchange --help`.

## Результаты

За 2 секунды каждый узел прошёл 21 274 раунда, в статистику попали 21 174 (без первых 100). VERIFY на всех узлах: PASS.

| ПК | Среднее, мкс | Медиана, мкс | Максимум, мкс | Раундов от 200 мкс |
| --- | --- | --- | --- | --- |
| user | 90,4 | 90,5 | 175,9 | 0 |
| pc1 | 91,2 | 91,3 | 184,1 | 0 |
| pc4 | 90,8 | 90,9 | 260,0 | 2 |

На user и pc1 все раунды уложились в 200 мкс. На pc4 два раунда из 21 174 вышли за порог (до 260 мкс), то есть в 200 мкс уложились 99,99% раундов.

Данные по каждому раунду лежат в папке `results`: `node0.csv` (user), `node1.csv` (pc1), `node2.csv` (pc4). В них столбцы `node_id, round, prepare_us, send_us, exchange_us, wait_us, compute_us, peer_blocks, retries, status`, время в микросекундах.

Гистограммы строятся скриптом `plot_hist.py` (нужны pandas, matplotlib и seaborn):

```bash
python3 plot_hist.py
```

Скрипт берёт раунды после разогрева со статусом 0 и сохраняет два графика: `hist_all.png` (все три ПК на одном графике) и `hist_by_pc.png` (отдельно по каждому ПК).


### Отдельные функции

- `load_config()` загружает параметры из файла;
- `send_data()`, `send_hello()`, `send_verify()` отправляют пакеты;
- `receive_for_round()` принимает пакеты одного раунда.

### Загрузка параметров из файла

С флагом `--config FILE` программа читает параметры из файла. В файле те же параметры, что и в командной строке, через пробел или с новой строки. Пример: `test.conf`.

Если параметр есть и в файле, и в командной строке, берётся значение из командной строки.

```bash
./exchange --config test.conf --dump-config
```

`--dump-config` печатает итоговые параметры и завершает программу, сеть при этом не запускается.

### Фаззинг через zzuf

zzuf не умеет портить аргументы командной строки напрямую, он портит данные, которые программа читает из файлов. Поэтому для фаззинга параметры командной строки записываются в файл `test.conf`: zzuf случайно меняет в нём биты, и программа запускается с испорченным файлом.

```bash
sudo apt install zzuf
chmod +x fuzz.sh
./fuzz.sh
```

Скрипт берёт 4 уровня порчи (`-r 0.004`, `0.01`, `0.05`, `0.2`) и по 200 разных seed на каждый. Результаты пишутся в `fuzz/results.csv`, а файлы, на которых программа упала, сохраняются как `fuzz/crash_*.conf`.

Код возврата:
- 0: параметры прочитались;
- 1: программа отказалась от испорченных параметров и вышла с ошибкой;
- 128 и больше: программа упала.

Для более строгой проверки можно собрать программу с проверкой памяти и запустить скрипт ещё раз:

```bash
gcc -O1 -g -fsanitize=address,undefined -std=gnu11 main.c -o exchange -lm
```

### Падение программы и анализ core в gdb

Флаг `--crash` вызывает функцию `crash_program()`, которая пишет число по нулевому указателю, и программа падает с SIGSEGV. `volatile` нужен, чтобы компилятор не считал эту запись невозможной и не выбросил её при оптимизации.

Для gdb удобнее собрать без оптимизации:

```bash
gcc -O0 -g -std=gnu11 main.c -o exchange -lm
ulimit -c unlimited
sudo sysctl -w kernel.core_pattern=core.%e.%p
./exchange --crash
gdb ./exchange core.exchange.*
```

Команды в gdb:

```
bt
info locals
frame 1
list
```

`bt` показывает, что программа упала в `crash_program()`, которую вызвал `main()`, а `info locals` показывает `p = 0x0`.
